2.1 VISAO GERAL
--------------------------------------------------------------------------------
A arquitetura e em CAMADAS, com fluxo de dados unidirecional. Cada camada so
conhece a camada imediatamente abaixo dela:

    TELA (screens/)
      |  chama
      v
    HOOK (hooks/)              <- estado: dados, loading, error
      |  chama
      v
    SERVICE (services/)        <- funcao fina, so monta a chamada HTTP
      |  usa
      v
    API CLIENT (configs/api)   <- axios + interceptor que injeta o token
      |  HTTP
      v
    BACKEND (Spring, projeto separado)

O ganho e isolamento: a tela nunca sabe que existe axios; o service nunca sabe
que existe React. Trocar o cliente HTTP mexe em um arquivo so.

2.2 ARVORE DE PASTAS
--------------------------------------------------------------------------------
  index.ts                    ponto de entrada (registerRootComponent)
  App.tsx                     providers + declaracao das rotas
  app.json                    configuracao do Expo

  assets/                     imagens do mascote

  src/
    screens/      telas completas, uma por rota
    components/   pecas reutilizaveis de UI

2.4 AUTENTICACAO
--------------------------------------------------------------------------------
Toda a autenticacao vive em src/contexts/AuthContext.tsx, que e o UNICO
estado verdadeiramente global da aplicacao.

  Estado exposto:  user, loading, error
  Acoes expostas:  login(), register(), logOut()

  Ciclo de vida:

  1. INICIALIZACAO (useEffect no mount)
     - le o token do SecureStore (chave "token")
     - se nao existe: user = null, segue para as telas publicas
     - se existe: chama GET /auth/me para validar e reidratar o usuario
     - se a chamada falha (token expirado): apaga o token e zera o user
     - enquanto isso, o provider renderiza um ActivityIndicator e NAO
       renderiza a arvore de telas (flag "initializing")

  2. LOGIN / CADASTRO
     - chama o service, guarda o token no SecureStore, seta o user
     - em caso de erro, preenche o estado "error" via getMessageError()
     - devolve null em caso de falha, para a tela decidir o que exibir

  3. LOGOUT
     - zera o user e apaga o token do SecureStore

  O TOKEN NUNCA E PASSADO MANUALMENTE. O interceptor em src/configs/api.ts
  le o SecureStore a cada requisicao e injeta o header
  Authorization: Bearer <token> automaticamente.

2.6 MODELO DE DOMINIO
--------------------------------------------------------------------------------
A hierarquia do conteudo educacional tem quatro niveis:

    MATERIA (Subject)

3.2 PADRAO DOS SERVICES
--------------------------------------------------------------------------------
Um service e uma funcao fina: monta a chamada, tipa a resposta, devolve
response.data. Nao trata erro (deixa propagar para o hook) e nao guarda
estado.

    export async function subjectGetAll(): Promise<Array<SubjectResponse>> {
        const response = await api.get<Array<SubjectResponse>>('/subject');
        return response.data;
    }

3.3 PADRAO DOS HOOKS DE DADOS
--------------------------------------------------------------------------------
Todos os hooks de dados seguem exatamente a mesma forma - useSubject,
useTopic, useQuestion e useAlternative sao estruturalmente identicos:

    - tres estados: <dado>, loading, error
    - uma funcao async que executa a busca
    - try / catch / finally:
        try:     chama o service e guarda o resultado
        catch:   traduz o erro com getMessageError() e guarda em "error"
        finally: sempre desliga o loading
    - retorna um objeto { funcao, loading, error, dado }

Exemplo (useSubject):

    const getAll = async () => {
      setLoading(true);
      setError(null);
      try {
        const response = await subjectGetAll();
        setSubject(response);
        return response;
      } catch (error) {
        const errorMessage = getMessageError(error, "Erro na busca de materias");
        console.error("Subject error:", errorMessage);
        setError(errorMessage);
        return null;
      } finally {
        setLoading(false);
      }
    };

A consistencia e o ponto forte do projeto: quem entende um hook entende
todos.

3.4 TRATAMENTO DE ERROS
--------------------------------------------------------------------------------
Centralizado em src/utils/getMessageErrorUtils.ts. A funcao recebe o erro
desconhecido e uma mensagem de fallback, e resolve em cascata:

    1. e um erro do axios?  -> usa response.data.message (mensagem do backend)
    2. e um Error comum?    -> usa error.message
    3. nenhum dos dois?     -> usa o fallback

Nenhuma tela monta mensagem de erro na mao. A mensagem resultante e exibida
pelo componente <ErrorMessage message={error} />, que se auto-oculta quando
a mensagem e nula.

3.5 ESTILIZACAO
--------------------------------------------------------------------------------
Tres niveis, do mais generico ao mais especifico:

  1. src/styles/colors.ts    paleta COLORS, agrupada por funcao (marca,
                             texto, fundos, bordas, superficies, status)
  2. src/styles/theme.ts     mainStyles: estilos compartilhados entre telas
                             (component, primaryButton, secondaryButton...)
  3. StyleSheet local        cada tela declara seu proprio StyleSheet no fim
                             do arquivo, com comentarios de secao

  Sempre StyleSheet.create, nunca objeto inline solto - a excecao legitima
  sao valores que so existem em runtime (ex.: insets da safe area).

  Composicao por array, com o mais especifico por ultimo:
      style={[styles.card, isSelected && styles.cardSelected]}

  OBSERVACAO: varias telas ainda tem cores em hexadecimal literal em vez de
  usar COLORS (SubjectsScreen e TabBar sao os casos mais visiveis).

3.6 NAVEGACAO TIPADA
--------------------------------------------------------------------------------
  src/types/navigation.ts declara RootStackParamList: o nome de cada rota e
  os parametros que ela recebe.

  src/hooks/useNavigation.ts exporta useAppNavigation(), um wrapper que ja
  devolve o objeto de navegacao tipado. As telas usam esse hook, nunca o
  useNavigation cru - assim o autocomplete funciona e um nome de rota errado
  vira erro de compilacao.

  Para ler parametros, o padrao e:
      const route = useRoute<RouteProp<RootStackParamList, "TopicsScreen">>();

  Apos login e logout usa-se navigation.reset() em vez de navigate(), para
  limpar a pilha e impedir o "voltar" para uma tela que nao faz mais sentido.

3.7 SAFE AREA
--------------------------------------------------------------------------------
Como o app roda em edge-to-edge, cada borda da tela precisa ser compensada
por EXATAMENTE UMA camada. A convencao adotada:

  - Telas COM TabBar:  <SafeAreaView edges={["top"]}>  (a TabBar cuida do
                       rodape, somando insets.bottom a sua altura fixa)
  - Telas SEM TabBar:  a propria tela cuida das duas bordas

  A TabBar tem ALTURA FIXA (64dp) + insets.bottom. Nunca flex - componente de
  chrome tem tamanho proprio, so o conteudo usa flex: 1 para ocupar a sobra.

  Esse padrao esta aplicado na TabBar e na SubjectsScreen. As demais telas
  ainda usam paddingTop fixo (52 ou 92) para compensar a status bar, o que e
  um valor chutado que acerta por acaso em alguns aparelhos. Ver secao 7.

4. TELAS
================================================================================

Oito telas registradas no Stack.Navigator, todas sem header nativo.

4.1 WelcomeScreen  (rota inicial)
--------------------------------------------------------------------------------
  Splash de marca. Fundo em gradiente com o mascote, o nome "IntegraMente" e
  o slogan "Aprender do seu jeito". A tela inteira e tocavel.

  Ao tocar, consulta o AuthContext e decide o destino:
      usuario logado    -> HomeScreen
      sem usuario       -> FirstScreen

  Usa replace() para nao deixar o splash na pilha.

4.2 FirstScreen  (onboarding)
--------------------------------------------------------------------------------
  Apresentacao para quem nao tem conta. Mascote, titulo "Bem-vindo ao
  IntegraMente!" e dois caminhos:
      "Comecar agora"   -> AuthScreen com isLogin: false  (cadastro)
      "Ja tenho conta"  -> AuthScreen com isLogin: true   (login)

4.3 AuthScreen  (login e cadastro)
--------------------------------------------------------------------------------
  Tela unica para as duas operacoes, controlada pelo parametro de rota
  isLogin. Quando isLogin e false, mostra tambem os campos "Seu nome" e
  "Confirmar senha".

  Validacao local antes de chamar a API:
      - e-mail nao pode ser vazio
      - senha nao pode ser vazia
      - no cadastro: senhas devem coincidir, minimo 6 caracteres,
        nome obrigatorio

  Tem um checkbox "Mostrar senha" que alterna secureTextEntry, e um link no
  rodape que alterna entre login e cadastro via replace().

  Em caso de sucesso, faz navigation.reset() para HomeScreen.

4.4 HomeScreen  (dashboard)
--------------------------------------------------------------------------------
  Tela principal pos-login. Saudacao personalizada ("Ola {nome}"), lendo o
  nome do AuthContext.

  Dois cards:
      "Atividade do dia"    -> card destacado, conteudo ainda FIXO
                               (Matematica / Contagem de objetos)
      "Continue seus estudos" -> card com o mascote, botao "Continuar jornada"
                                 que leva a ActivityScreen

  Exibe a TabBar. Exceto o nome do usuario, o conteudo ainda nao vem da API.

4.5 SubjectsScreen  (materias)
--------------------------------------------------------------------------------
  Lista as materias vindas de GET /subject, em grid de dois por linha.

  Usa useSubject(), busca no mount via useEffect, exibe <ErrorMessage> em
  caso de falha. Tocar num card navega para TopicsScreen levando subjectId e
  subjectName como parametros.

  E a tela que ja segue o padrao correto de safe area (edges={["top"]}).
  Todos os cards ainda usam o mesmo emoji (compasso), sem icone por materia.

4.6 TopicsScreen  (topicos da materia)
--------------------------------------------------------------------------------
  Recebe subjectId e subjectName por parametro e lista os topicos daquela
  materia via GET /topic/:subjectId, usando useTopic().

  Cada card mostra o status (badge a esquerda), titulo, subtitulo e o
  percentual de conclusao (pill a direita). Tem cabecalho proprio com o nome
  da materia e um balao do mascote explicando a tela.

  Ha estilos ja preparados para os tres estados visuais (concluido, em
  andamento, bloqueado), mas eles ainda nao sao aplicados condicionalmente -
  o valor cru do enum e renderizado como texto no badge.

4.7 ActivityScreen  (atividade)
--------------------------------------------------------------------------------
  A tela mais elaborada tecnicamente. Implementa uma atividade de ADICAO
  (4 + 3) com interacao por arrastar:

      - dois grupos de bolinhas (4 e 3) sao arrastaveis via Gesture.Pan
      - um alvo fixo marca onde elas devem ser soltas
      - measure() calcula a posicao absoluta de cada elemento na tela e
        guarda a distancia em useSharedValue (evita re-render)
      - ao soltar, calcula a distancia euclidiana ate o alvo; se for menor
        que 60dp, a bolinha "gruda" com withSpring(); senao volta ao lugar
      - so depois que OS DOIS grupos estao no alvo, runOnJS libera as
        alternativas de resposta (5, 7, 9) para toque

  Toda a logica de animacao roda na UI thread via Reanimated.

  IMPORTANTE: o conteudo e 100% fixo. A tela nao recebe parametros e nao
  consome a API. O comentario em types/navigation.ts registra a intencao de
  que ela receba a atividade e renderize por componentes reutilizaveis
  conforme o tipo.

4.8 ProfileScreen  (perfil)
--------------------------------------------------------------------------------
  Avatar com o mascote, nome do usuario, e uma linha de estatisticas
  (estrelas, atividades, dias de sequencia) - todas com valores FIXOS.

  Menu com quatro itens: Conquistas, Acessibilidade, Editar dados e Sair.
  Apenas "Sair" esta implementado: chama logOut() e faz reset() para a
  WelcomeScreen. Os outros tres nao tem acao.

4.9 SchoolYearScreen  (ano escolar) - NAO REGISTRADA
--------------------------------------------------------------------------------
  Tela de selecao do ano do Ensino Medio (1o, 2o ou 3o), com cards
  selecionaveis usando o enum Escolaridade.

  ESTA TELA NAO ESTA NO Stack.Navigator e portanto e inalcancavel. Ela
  existe no arquivo e no RootStackParamList, mas nao foi registrada em
  App.tsx. Alem disso, tenta desestruturar userLogin e userRegister do

  Corresponde a uma funcionalidade planejada e nao concluida: escolher a
